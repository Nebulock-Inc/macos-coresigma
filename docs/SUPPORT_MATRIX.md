## What the cells mean

- **✅ fires**: the query had at least one hit inside at least one clean simulation window. This is not attribution to the simulated chain: a hit can come from anything the host did in those seconds.
- **🔶 noisy**: in the idle window the query had more hits per hour than its level allows (critical and high: 5/h, medium: 20/h; low and informational are never noisy). The capture harness's own commands are left out. Noise also counts a private laptop sample (2.0 h of an ESF capture, 0.3 h of slices of a longer ESF log and 2.6 h of unified log), each rule at the higher of its EQL and its Sigma-semantics count; no laptop data is published, only each rule's noisy or quiet outcome, and `laptop: not counted` where the sample didn't count it.
- **⚪ silent**: the query converts and runs, with no hit in any clean window and no noise.
- **converts**: the query converts; there is no store here to run it.
- **not-run** (Falcon): Falcon wasn't queried in every clean window, and the rule fires on another target, so no Falcon hit in the windows it was queried in doesn't make it silent.
- **✗ fails**: the rule doesn't convert for the target, or the store rejected the query.
- **field-absent**: the query uses a field that no replayed document has.
- **not-verified** (Jamf Protect): deferred to the next release.
- **Status**: `verified` if the rule fires on at least one target (Falcon included); otherwise `not-verified`, with the reason in a footnote. A rule that is only noisy is not-verified, and so is a rule whose only hits are not the behaviour it looks for.

## Target notes

- Defender / Sentinel (KQL): converts with a product-agnostic Windows-schema mapping; whether Defender populates those tables for macOS is unverified.
- Elastic Defend: convert-only, with coreSigma's ECS mapping; fields were not checked. Elastic Defend 9.5.6 data from the test host exists: Defend reports a new file only as a modification, so the file_event scope misses creates there (see the README's [Known limitations](../README.md#known-limitations)).
- Elastic ES|QL matches plain Sigma strings case-sensitively (pysigma-backend-elasticsearch).
- `$` in a `|re` pattern is literal in Lucene, EQL and ES|QL regular expressions, so such a pattern can't match there.
- Elastic EQL's `regex~` matches `|re` case-insensitively.
- OpenSearch maps the path and command fields as lowercase keywords, so `|re` matches case-insensitively there; plain keyword fields (unified_log.subsystem, signing IDs) match case-sensitively.
- Kibana (`scripts/deploy_sigma_rules.py`) deploys each rule in the form that converts: an EQL rule for each single-event rule and each temporal_ordered correlation, an ES|QL rule for each other correlation. So the Elastic EQL and Elastic ES|QL columns together are what Kibana runs.
- Order: Elastic EQL and ClickHouse enforce a temporal_ordered correlation's order. EQL runs it as a `sequence` with `maxspan`; on ClickHouse the matrix tool rewrites pysigma-backend-clickhouse's query, which checks no order, to use `windowFunnel` over the timespan (`clickhouse_ordered` in `scripts/rule_matrix.py`). ES|QL has no temporal_ordered, and Splunk runs it as temporal (the rule's declared fallback), in any order.
- ClickHouse (pysigma-backend-clickhouse) groups the other correlations over the whole search range, not per timespan. A temporal correlation there needs last − first ≤ timespan over the whole group, so over a long range ClickHouse can also miss a chain and understate noise, as well as add fires. Either way it is a backend limit, not a rule bug.
- Splunk and ES|QL correlations count in fixed windows of the timespan (`bin`, `date_trunc`): a chain that crosses a window boundary is missed. An EQL sequence's `maxspan` and ClickHouse's `windowFunnel` window start at each first event.
